# /lagune-charter

🧬 プロジェクトがどんなものかを **Lagune** に伝えると、それをセキュリティのルールに落とし込みます（説明がなくても、プロジェクトそのものからルールを導き出します）。

charter は全体を統括するレイヤーで、後続のすべてのフェーズが守らなければならない、セキュリティ優先の原則をまとめたものです。プロジェクトのセキュリティ態勢に対するコンパイル時チェックだと考えてください。

## 実行方法

<Tabs>
  <TabItem value="describe" label="説明する" default>

```prompt
/lagune-charter このプロジェクトは、ゲームソフトを販売するオンラインストアです。顧客は商品をカートに入れ、クレジットカードか銀行振込で支払います。自分の注文と、それぞれの注文の状況を確認できます。
```

  </TabItem>

```prompt
/lagune-charter
```

> _決済ライブラリ、ログインの仕組み、顧客に紐づいた注文モデルがあります。何かを販売するオンラインストアのようです。顧客は支払いをして、自分の注文を追跡します_…… ☁️

  </TabItem>

## 導き出す内容

**Lagune** は説明や **PRD** を方向性として受け取り、それがセキュリティ面で何を意味するかを導き出したうえで、プロジェクトを読み取って、説明に含まれていない点まで掘り下げます。たとえば：

- カートが注文を保持しているということは、**データベース**があるということです。
  - 例：`"データはどこに保存されているか？"`、`"誰がアクセスできるか？"`、`"漏えいしていないか？"`。
- 顧客が自分の注文を確認できるということは、何らかの**ログインやアクセス制御**があるということです。
  - 例：`"ある顧客が別の顧客の注文にアクセスできないか？"`、`"セッションは保護されているか？"`。
- カードと銀行振込での支払いを受け付けるということは、**お金と機密データが関わる**ということです。
  - 例：`"カード情報は保存されているか？"`、`"支払いは検証されているか？"`。

説明とプロジェクトは互いに補い合います。説明が意図を定め、依存関係や README、設定を読み取ることで、説明に含まれていなかった点が浮かび上がります。それでも重要な点がはっきりしない場合、**Lagune** は推測せず、短くわかりやすい質問をします。

そこから **Lagune** は、プロジェクトに合わせたセキュリティルールを組み立てます。ルールは必要なときにいつでも見直し、調整できます。

:::tip[活用のヒント]

- プロジェクト独自のセキュリティルールを定義することもできます。
- 関連する情報を詳しく伝えるほど、最終的なレポートの質が上がります：
  - プロジェクトの概要、仕組み、内部で何が起きているかを説明してください。
  - エンドユーザーは誰ですか？ユーザーにできることと、できないことは何ですか？
  - 振る舞いに関する情報は、技術的な情報と同じくらい価値があります。
- charter の記録は `.lagune/memory/charter.md` にあります。

:::

## 記録するカテゴリ

専門知識は後続のフェーズが必要なときだけ読み込むセキュリティの知識で、プロジェクトの [カタログ](/docs/catalog) には [カテゴリ](/docs/categories) 単位で加わります。プロジェクトにまだカテゴリが記録されていない間は、charter がプロジェクトを読み取って裏付けが得られたカテゴリ（プロジェクトの言語、LLM の呼び出し、コンテナーなど）をそれぞれ記録し、要約でその名前を示します。

カテゴリが記録されたあとは、charter はそれらに手を加えず、プロジェクトでまだ使っていないカテゴリの名前を挙げるだけです。カテゴリはいつでも自分で変更できます：

```bash
npx lagune write add --categories python
npx lagune write remove --categories python
```
