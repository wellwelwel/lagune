# Hardcoded-secret vulnerabilities

> - This knowledge extends your judgment. Apply what fits the project and keep reasoning beyond the list.
> - Source: OWASP, <https://cheatsheetseries.owasp.org/>, with **GitHub** Docs, "Removing sensitive data from a repository", the **Next.js**, **Nuxt**, **Expo**, **SvelteKit**, **Astro**, **Vite**, **Create React App**, **Vue CLI**, and **Gatsby** documentation on the variables they ship to the browser, the **Android** documentation on the debug keystore, the **Docker** documentation on `host.docker.internal`, and the **dotenvx** documentation on encrypted environment files.

## Rules

- This specialization audits and explains.
- By default, it never rewrites your code.

## What to look for

A **secret compiled into the artifact** is a credential (an API key, a token, a password, a private key) that lives in the source instead of in the environment or a secret store, or a file committed with the code that exists to hold one, such as a key file, a keystore, or a **Terraform** state, which records the secrets of the resources it manages in plain text. It ships to everyone with repo access and stays in history forever, so a single leak of the code is a leak of the credential. The defect is decidable from the repository alone: a literal, not a lookup, or a credential file **Git** tracks. Two neighbours belong elsewhere: a secret in a `.tf`/**Kubernetes** manifest is `infra` (its `secrets-in-data` check), and how a validated secret is stored or rotated is `crypto` (key management).

### Deterministic pre-pass

Run the secrets hook first. It is deterministic and its verdict is literal. In the source, it keys on **provenance** (a literal versus an environment lookup), not on the value's contents, so it does not depend on an exhaustive catalog of provider prefixes and produces almost no false positives. For a credential or environment file, it keys on the file's name, on what its content proves, and on whether **Git** tracks or ignores it.

Call `lagune_read` with `command` set to `secrets` to scan the whole project, or add `arguments` set to `["--dir", "<DIR>"]` for a directory or `["--file", "<FILE>"]` for a single file.

It prints up to three sections, each weighed by its evidence. **Hardcoded secrets found** is proof of an exposed secret and exits non-zero: a hardcoded fallback for an environment secret (`process.env.X ?? "..."`), a credential embedded in a connection string to a remote host, a value matching a curated provider format (**AWS** `AKIA...`, **GitHub** `ghp_...`, **Stripe** `sk_live_...`, a PEM private key), a credential file **Git** tracks (a private key or keystore, cloud or service account credentials, a **Terraform** state, or an `.npmrc`, `.pypirc`, kubeconfig, or **dotenvx** `.env.keys` that holds a credential), or an environment file **Git** tracks that holds one of those formats or connection strings.

**Secret handling to review manually** is plausible but unconfirmed: a plain literal bound to a secret-named identifier, in the source or in an environment file (its name and shape cannot prove it a real credential rather than a development default, a hash, or a public key), a connection string to a local database (on a loopback address, `0.0.0.0`, **Docker**'s `host.docker.internal`, or a single-label host such as a **Docker Compose** service), a secret-named value flowing into a log or response sink, a `.key` or `.pem` file whose content it cannot recognize, a credential file in a test folder, a file it could not read, and one entry naming why it cannot read the project's **Git** state, such as a worktree or submodule whose index lies outside the project. Read each by hand.

**Secret handling advisories** does not change the exit code and holds a real risk not yet exposed: a credential file, or an environment file holding proof of a secret, that **Git** neither tracks nor ignores, so the next `git add` stages it, and a local environment file, such as `.env.local`, that **Git** tracks or would commit, since the next secret written there lands in a commit. It stays silent on a look-alike, such as a committed `.env` of public defaults, a **dotenvx** ciphertext, a **Keynote** deck saved as `.key`, or **Android**'s `debug.keystore`, and on what **Git** ignores. A clean run prints a single line.

Flagging a committed secret by its format is standard defensive tooling (**gitleaks**, **trufflehog**, and **GitHub** push protection do the same), shipping detection signatures, never a live secret.

### Reading beyond the hook

- **Split or obfuscated literals:** a token assembled from concatenated parts (`"ghp_" + "..."`) or base64-wrapped to dodge a scanner is the same defect. Treat the assembly as a lead and confirm by resolving it.
- **Secrets in the wrong file:** a credential in a checked-in config or in a template such as `.env.example`, or a key beside the data it protects. The hook skips templates and other config formats by design, and stays silent on a tracked environment file that holds no provider format, connection string, or secret-named value, so read each of them for a value not meant to be public. It also misses a credential under a name it does not know, such as a renamed copy of a key.
- **A secret that reached a client bundle:** a key inlined into front-end code is public the moment it ships. A variable under a prefix its framework ships to the browser (`NEXT_PUBLIC_`, `NUXT_PUBLIC_`, `EXPO_PUBLIC_`, `PUBLIC_`, `VITE_`, `REACT_APP_`, `VUE_APP_`, `GATSBY_`) is exposed on purpose and must never hold a real credential. The hook flags one only by a provider format, never by its name, so read the others yourself.

Safer shape: keep every credential out of source, config, and version control, and read it from the environment or a secrets manager at runtime. A credential file stays where the tool that reads it expects it, untracked with `git rm --cached` and covered by a `.gitignore` rule, so no later commit adds it back. An environment file **Git** tracks holds only public defaults or values encrypted with **dotenvx**, whose `.env.keys` stays out of **Git** like any credential file, and every other secret lives in a local variant **Git** ignores, such as `.env.local`. A credential that ever reached a commit stays burned after the fix, and only rotating it where it was issued ends the exposure. Purging it from the history is the user's decision, never part of a fix: the purge rewrites the commit that leaked it and every one after, forces every collaborator to rebase or re-clone, and still misses every clone, fork, and mirror already taken.

Does not close it: moving the literal into a committed `.env`, a template such as `.env.example`, or a checked-in config, or keeping it as the hardcoded fallback of an environment lookup, since the working tree still holds the literal either way. Nor does a `.gitignore` rule alone, since it never untracks a file **Git** already tracks.

## How to act on the result

- **In detect (detection):** each entry under **Hardcoded secrets found** is a finding. Record what it is (a committed credential), why it matters (anyone who can read the code holds the secret), and the evidence (the file, and the identifier when there is one). Each entry to review manually is a lead to confirm, not a finding: read the value and how the code uses it, and record a finding only for a real credential, never for a development default or a key made only for tests. For a credential file in a test folder that only the tests use, tell the user its path can be left out in the project's configs, and leave that choice to them. An advisory is a real risk not yet exposed, never a finding: raise it with the user and name the change that keeps the file out of a commit, such as its `.gitignore` rule. Confirmed leads flow through detect's normal steps and are tracked like any other finding. The entry the hook prints when it cannot read the project's **Git** state is not a finding the code can settle: record it once under Not determined, naming its cause and asking whether the files it lists are committed, never as one entry per file. For each credential finding, also record a side quest under Not determined asking whether that credential has been rotated: name it by what it unlocks, never by its value or the finding's name, so the side quest outlives the finding.
- **In verify (proof):** the control holds once the code reads the credential from the environment or a secret store and the working tree no longer holds the literal in any form, except in a file **Git** ignores and does not track, such as `.env.local`, or as a **dotenvx** ciphertext. For a credential or environment file, it holds once the hook reports neither that file nor the local file its secret moved to, as a finding or an advisory. A lead the hook still prints there keeps the finding open only once you confirm it is a real credential still exposed. One you cannot confirm, such as the entry for a **Git** state the hook cannot read, never keeps it open, not even as inconclusive: name it in the summary as unconfirmed, so the user settles it before confirming the stand-down. Neither the history nor the credential's rotation keeps the finding open either, since both lie outside the working tree. Instead, point the summary at detect's rotation side quest, so the user never mistakes a closed finding for a safe credential. If the risk is not closed, record it as such and point back to harden.
