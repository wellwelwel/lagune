Riferimenti e fonti

Fonti OWASP

Da dove proviene la conoscenza delle specializzazioni OWASP integrate, collegata alle relative pagine canoniche di attacchi e Cheat Sheet di OWASP.

Questo documento collega ogni attacco (www-community) e ogni Cheat Sheet (CheatSheetSeries) di OWASP a una categoria di sicurezza, ognuno con il link alla sua pagina pubblica canonica. All'interno di una categoria, gli elementi equivalenti condividono un'unica riga dell'elenco: gli attacchi e le cheat sheet che affrontano lo stesso rischio sono elencati insieme, separati da virgole. Gli elementi senza un equivalente diretto stanno su una riga a sé.

  • Il merito è di OWASP. Gli attacchi si trovano in https://owasp.org/www-community/attacks/<attack> e le cheat sheet in https://cheatsheetseries.owasp.org/cheatsheets/<cheat>.html.

25. Logica di business e abuso delle funzionalità​

La logica di business e l'abuso delle funzionalità non hanno un'unica superficie nel codice che una specializzazione per superficie possa difendere: la difesa è una progettazione specifica dell'applicazione, lo stesso ragionamento che guida il threat modeling del progetto. Spostati in "Fuori ambito".

31. Cloud, container e infrastruttura​

La configurazione di container e workload è configurazione come codice che lo sviluppatore distribuisce con l'app (Dockerfile, Compose, securityContext dei Pod), una superficie reale che harden corregge e verify dimostra, quindi rientra nell'ambito. L'amministrazione del cluster (RBAC, etcd, API server, admission, segmentazione della rete) è dominio dell'operatore e resta fuori ambito.

  • Docker Security, Node.js Docker (container)
  • Kubernetes Security (container: la parte di workload e Pod. L'amministrazione del cluster resta fuori ambito)
  • Serverless / FaaS Security (serverless)

32. Supply chain e CI/CD​

  • NPM Security (interpreter)
  • Dependency Graph & SBOM Best Practices, Vulnerable Dependency Management (interpreter)

33. Segreti e configurazione​

La gestione dei segreti è operativa: vault, CI/CD, configurazione del cloud, rotazione. L'unico aspetto a livello di codice (un segreto scritto nel sorgente) è un'analisi deterministica, non una specializzazione di rischio. Spostati in "Fuori ambito".

34. Processi, progettazione e governance​

La tutela della privacy degli utenti è una questione di politiche e di progettazione (minimizzazione dei dati, trasparenza, conservazione), non una superficie nel codice che una specializzazione difende. Spostata in "Fuori ambito".

35. Pagamenti e conformità​

  • Secure Integration of Third-Party Payment Gateways (payment)

36. Embedded, IoT e domini specializzati​

La sicurezza automobilistica e quella dei droni sono domini dei sistemi embedded (bus CAN, firmware OTA, integrità di sensori e radio, accesso fisico), non il sorgente di applicazioni web e API che Lagune verifica. Spostate in "Fuori ambito".

Fuori ambito (nessuna superficie nel codice)​

Questi non sono terreni da specializzazione e non hanno casella di spunta: sono governance, processi, hardening operativo o uso di framework, senza un'unica superficie nel codice che una specializzazione per superficie possa difendere. Il loro valore per la sicurezza è reale, ma risiede nei processi e nell'architettura (o, per un framework, nella skill del linguaggio stesso), non in una difesa fornita da questo catalogo. Sono elencati come riferimento, non come lavoro da fare.

  • Authorization Regression Testing, Authorization Testing Automation
  • JAAS
  • Denial of Service, Denial of Service
  • HTTP/2 Reset Attack
  • Traffic flood
  • Web Service Amplification Attack (amplificazione tramite SOAP e WS-Addressing, una variante operativa di DoS senza superficie nel codice)
  • Cash Overflow
  • Spyware, Trojan Horse (malware che colpisce l'utente finale, non una superficie nel codice del progetto verificato. L'aspetto della distribuzione tramite browser si trova in browser)
  • REST Security, REST Assessment
  • Web Service Security
  • Cloud Architecture Security (progettazione e compromessi: IAM contro URL firmati, VPC pubbliche e private, confini di fiducia, responsabilità condivisa. A differenza di container, non ha una configurazione concreta che una specializzazione controlli)
  • Infrastructure as Code Security (nonostante il nome, riguarda il processo SDLC e gli strumenti per gestire l'IaC: plugin per IDE, analisi statica, analisi delle immagini, CI/CD, firma. Non offre alcun passaggio da pattern non sicuro a forma sicura in un file Terraform o CloudFormation)
  • Kubernetes Security (solo la parte di amministrazione del cluster: RBAC, etcd, API server, admission. La parte di workload e Pod rientra nell'ambito sotto container)
  • Network Segmentation (architettura di rete e politiche del firewall)
  • Subdomain Takeover Prevention (ciclo di vita e monitoraggio del DNS, non codice)
  • Secrets Management (vault, CI/CD, rotazione. L'aspetto dei segreti scritti nel codice è un'analisi deterministica, non una specializzazione di rischio)
  • C-Based Toolchain Hardening (flag di compilatore, linker e build, senza alcun sink nel sorgente)
  • Microservices Security, Microservices based Security Arch Doc
  • Zero Trust Architecture
  • CI/CD Security, GitHub Actions Security
  • Software Supply Chain Security
  • Error Handling, Full Path Disclosure (configurazione del gestore globale degli errori per ogni stack. La fuga è la stessa divulgazione che la gestione degli errori già governa)
  • Abuse of Functionality, Business Logic Security, Abuse Case (historical) (progettazione specifica dell'applicazione, senza un unico sink nel codice)
  • User Privacy Protection (minimizzazione dei dati, trasparenza, politica di conservazione)
  • Top 10 Automotive Security Vulnerabilities, Drone Security (domini dei sistemi embedded: bus CAN, firmware OTA, integrità di sensori e radio, non sorgente web o API)
  • Mobile Application Security (hardening delle piattaforme Android e iOS: archiviazione, biometria, pinning, dati personali. Non ha un'unica superficie nel codice, e l'aspetto del caricamento di codice non attendibile è passato a interpreter)
  • Threat Modeling, Threat Modeling (community page)
  • Attack Surface Analysis
  • Secure Product Design
  • Secure Code Review
  • Virtual Patching
  • Vulnerability Disclosure
  • Legacy Application Management
  • Security Terminology
