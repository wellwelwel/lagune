การใช้ tokenสูงกว่า แต่แยกขาดจากกัน ซับเอเจนต์แต่ละตัวสแกนในบริบทของตัวเอง
/lagune คุณคือ orchestrator ด้านความปลอดภัยไซเบอร์ที่ใช้ Lagune เพื่อแจกแจง path ส่งซับเอเจนต์ 1 ตัวต่อ 1 path และรวมรายงานของซับเอเจนต์ทั้งหมด (ซับเอเจนต์เป็นผู้อ่านเนื้อหาทั้งหมด)

คุณต้องมอบหมายงานให้ซับเอเจนต์ตามขนาดของโปรเจกต์ปัจจุบัน: ยิ่งโค้ดเบสใหญ่ ยิ่งต้องส่งซับเอเจนต์มากขึ้น โดยรันทั้งหมดขนานกัน และให้ prompt ด้านล่างนี้กับซับเอเจนต์แต่ละตัว:

```prompt
/lagune คุณคือนักวิจัยด้านความปลอดภัยไซเบอร์ที่เชี่ยวชาญด้านความปลอดภัยเชิงป้องกันอย่างลึกซึ้ง และใช้ Lagune เพื่อเพิ่มความรู้และความแม่นยำของคุณ

สแกน <path> ด้วยตัวเอง และจับคู่จุดบกพร่องทุกจุดที่พบกับการแก้ไขที่เป็นรูปธรรม นี่คือการสแกนแบบแยกเดี่ยว ไม่ใช่ขั้นตอนแบบ Blue Team: ห้ามรัน detect, plan, harden หรือ verify และห้ามเขียนอะไรลงในการติดตามของ Lagune

สุดท้าย แสดงรายการจุดบกพร่องทุกจุดใน <path> พร้อมระดับความรุนแรงและการแก้ไขที่เป็นรูปธรรมของแต่ละจุด
```

สุดท้าย รวมรายงานของซับเอเจนต์ทั้งหมดเป็นรายการจุดบกพร่องและการแก้ไขรายการเดียวที่เรียงตามลำดับความสำคัญ

🪄 การตรวจจับแบบจำกัดขอบเขต​

ชี้คำสั่ง /lagune-detect ไปที่บางส่วนของโปรเจกต์แทนทั้งโปรเจกต์ อธิบายขอบเขตด้วยภาษาธรรมดา (commit, pull request หรือสถานการณ์จริง) แล้วคำสั่งจะทำแผนผังเฉพาะข้อตรวจพบที่เกี่ยวกับความปลอดภัยในส่วนนั้น

tip

ทุกสิ่งที่ตรวจพบในที่นี้เป็นข้อตรวจพบปกติ คุณจึงนำไปใช้ต่อกับ /lagune-plan, /lagune-harden และ /lagune-verify ได้ทันที โดยจำกัดขอบเขตไว้เฉพาะรายการเหล่านั้น

  • 📌 ตั้งแต่ commit หนึ่ง
  • 🔀 diff ของ branch หรือ PR
  • ⛑️ หลังเกิดเหตุ

ตรวจความปลอดภัยให้ชุด commit ใหม่โดยเฉพาะ จำกัดขอบเขตไว้แค่สิ่งที่ commit เหล่านั้นเปลี่ยน ตัวอย่างเช่น:

/lagune-detect จำกัดขอบเขตการตรวจจับไว้ที่ทุกสิ่งที่เปลี่ยนไปตั้งแต่ commit `a1b2c3d`

ตรวจความปลอดภัยของ pull request ก่อน merge โดยจำกัดขอบเขตไว้แค่ diff ของ pull request นั้น ตัวอย่างเช่น:

/lagune-detect จำกัดขอบเขตการตรวจจับไว้ที่การเปลี่ยนแปลงที่ branch นี้นำเข้ามาเมื่อเทียบกับ `main`

เล่าสิ่งที่เกิดขึ้นด้วยคำพูดของคุณเอง Lagune อ่านสถานการณ์ ไม่ใช่ flag แล้วเปลี่ยนเป็นการไล่ตรวจที่เจาะจง ตัวอย่างเช่น:

/lagune-detect เว็บไซต์ของเราเกิดข้อมูลรั่วไหลเมื่อไม่กี่สัปดาห์ก่อน ไม่รู้แน่ชัดว่าเกิดขึ้นได้อย่างไร และกังวลว่ายังมีช่องโหว่ที่เปิดอยู่ซึ่งอาจทำให้ข้อมูลรั่วอีก ไล่ตรวจโค้ดอย่างละเอียด เน้นทุกจุดที่มีการอ่าน จัดเก็บ หรือเปิดเผยข้อมูลที่ละเอียดอ่อน และทำแผนผังทุกอย่างที่อาจยังเป็นทางให้ข้อมูลหลุดออกไปได้ ให้ถือว่านี่คือเหตุการณ์จริง ไม่ใช่การซ้อม

🚨 การตรวจสอบแบบ Zero Trust​

ถือว่าทั้งเวิร์กสเปซและ dependency ทุกตัวเป็นปฏิปักษ์: การตรวจสอบนี้ไล่หา interpreter การเรียกเครือข่าย payload ที่ถูกเข้ารหัส และโค้ดที่ซ่อนอยู่ในที่ที่ไม่น่าเป็นไปได้เพื่อเล็ดลอดตัวสแกน แล้วจบด้วยผลตัดสิน go/no-go ว่าโปรเจกต์ปลอดภัยพอจะใช้หรือไม่

npx lagune write add --categories owasp ai javascript

เวลานานกว่า แต่ละเอียดกว่า สแกนไฟล์แบบขนานกัน แล้วรวมเป็นผลตัดสินเดียว
การใช้ tokenสูงที่สุด แต่ปลอดภัยที่สุด ซับเอเจนต์แต่ละตัวอ่านความรู้เฉพาะทางในบริบทแยกของตัวเอง
/lagune คุณคือ orchestrator ด้านความปลอดภัยไซเบอร์ที่ใช้ Lagune เพื่อแจกแจงไฟล์ ส่งซับเอเจนต์ 1 ตัวต่อ 1 ไฟล์ และสร้างรายงาน (ซับเอเจนต์เป็นผู้อ่านเนื้อหาทั้งหมด)

ส่งซับเอเจนต์ 1 ตัวต่อ 1 ไฟล์ โดยรันทั้งหมดขนานกัน และให้ prompt ด้านล่างนี้กับซับเอเจนต์แต่ละตัว โดยจำกัดขอบเขตไว้ที่ไฟล์ของตัวเอง:

```prompt
/lagune คุณคือนักวิจัยด้านความปลอดภัยไซเบอร์ที่เชี่ยวชาญด้านความปลอดภัยเชิงป้องกันแบบ zero trust อย่างลึกซึ้ง และใช้ Lagune เพื่อเพิ่มความรู้และความแม่นยำของคุณ

ถือว่า <file> เป็นแหล่งที่ไม่น่าเชื่อถือและเป็นขอบเขตที่อาจเป็นอันตราย ทุก interpreter, fetch, base64 และสิ่งที่คล้ายกัน ต้องถือว่าเป็นภัยคุกคามที่อาจเกิดขึ้น

ขยายการวิเคราะห์ไปถึงทุกสิ่งที่ <file> import รวมถึง dependency และ dependency ย่อย ซึ่งเป็นที่ที่โค้ดอันตรายอาจซ่อนอยู่เพื่อเล็ดลอดตัวสแกน

ความรู้เฉพาะทางที่ซับเอเจนต์ทุกตัวต้องใช้ (โหลดทีละตัวด้วย `npx lagune read catalog <name>`):

- interpreter
- secrets
- llm
- path

ย้ำให้ชัด: ช่องโหว่ทุกข้อที่ระบุได้ต้องถือว่าเป็นภัยคุกคามที่อาจเกิดขึ้น โดยไม่มีข้อยกเว้น

สุดท้าย ให้ผลตัดสินว่าโปรเจกต์นี้ปลอดภัยและน่าเชื่อถือพอให้ฉันใช้หรือไม่
```

สุดท้าย รวมรายงานของซับเอเจนต์ทั้งหมดเป็นผลตัดสินสุดท้ายเพียงผลเดียว
ก่อนหน้าsecretsถัดไปเอกสารระเบียบวิธี
